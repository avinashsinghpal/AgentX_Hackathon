## Issues Found

### 1. Stale password in documentation and examples

Severity: medium
Type: documentation/configuration drift

The running `.env` and Docker container use the configured `POSTGRES_PASSWORD`.
However, documentation and example files referenced the old value
`sellerresolve_local_password`:

- `README.md`
- `docs/runbook.md`
- `.env.example`

This mismatch causes PostgreSQL authentication failures when a user copies commands
from the documentation or from `.env.example` without replacing the password.

Evidence:

- A connection using `sellerresolve_local_password` fails with:
  `password authentication failed for user "sellerresolve"`
- A connection using the password from `.env` succeeds.
- PostgreSQL logs contain repeated `FATAL: password authentication failed for user "sellerresolve"`
  entries. The final two entries at `2026-11-11 06:35:23/24 UTC` were generated by an
  intentional verification probe using the stale documented password and confirm
  the root cause.

### 2. Duplicate-constraint and check-constraint errors in PostgreSQL logs

Severity: none (expected test behavior)
Type: test evidence, not application failure

PostgreSQL logs contain errors such as:

- `duplicate key value violates unique constraint "uq_orders_seller_order_number"`
- `insert or update on table "cases" violates foreign key constraint "fk_cases_seller_order"`
- `duplicate key value violates unique constraint "uq_seller_policies_one_active"`
- `new row for relation "order_items" violates check constraint "ck_order_items_quantity_positive"`
- `duplicate key value violates unique constraint "uq_tracking_events_shipment_provider_event"`
- `duplicate key value violates unique constraint "uq_audit_logs_chain_sequence"`
- `duplicate key value violates unique constraint "ix_audit_chain_state_chain_key"`

These correspond to intentional negative tests in
`apps/api/tests/test_database_constraints.py`, which assert that database-level
constraints reject invalid data. They are not production runtime failures.

### 3. Only the PostgreSQL service is running through Compose in this workspace

Severity: informational
Type: environment shape

`docker compose ps -a` shows only `sellerresolve-postgres`. The API and frontend are
running as host processes in this verification environment:

- API health endpoint: `http://127.0.0.1:8000/healthz` returned HTTP 200.
- Frontend: `http://localhost:3000/` returned HTTP 200.

This is consistent with the documented local development workflow, where `uvicorn`
and `pnpm run dev` run on the host and connect to Docker PostgreSQL. The Compose
`api` and `web` services were not started during this verification.

## Root Causes

1. Documentation and example configuration drifted from the actual configured
   PostgreSQL password. The live container and `.env` agree; the docs and
   `.env.example` did not.
2. Constraint errors in the PostgreSQL log are generated by tests that deliberately
   violate database constraints. They confirm that constraints are enforced by the
   schema.
3. No Docker volume or database initialization mismatch was found. The volume was
   initialized with the same user, database, and password currently present in
   `.env` and the container environment.

## Changes Made

No database, volume, migration, constraint, or authentication configuration was
changed.

the stale password:

- `README.md`

    to `<POSTGRES_PASSWORD>`.

    `<POSTGRES_PASSWORD>`.

    `POSTGRES_PASSWORD`.

    `POSTGRES_PASSWORD`.

`<POSTGRES_PASSWORD>` means the value of `POSTGRES_PASSWORD` from the local `.env`
file. It is intentionally not a runnable literal password.
