# SellerResolve Database, Policy Engine and Resolution Refactor Plan

Status: implementation plan produced from a direct audit of the repository.
Basis: the repository as it exists on branch `f1` (single commit `3a5773e`), not the specification text.

---

Migration chain: `73fa33a3a744` (empty baseline) -> `3d74bdde4fe4` (`create_core_domain_tables`, autogenerated with `sqlalchemy.dialects.sqlite.JSON`).

Money: `orders.total_amount` is an integer in minor units. `PolicySchema` money fields are integers in **major** units (rupees/dollars). `ResolutionTools` mixes them by dividing the order total by 100 and comparing against policy values, and it reads policy keys that the validated schema never produces.

## 2. Identified problems

1. SQLite-specific model types (`sqlalchemy.dialects.sqlite.JSON`) and a SQLite-first `DATABASE_URL`, with no PostgreSQL driver installed.
2. `ResolutionTools.evaluate_policy_rules` reads `refunds.auto_approve_max_amount`, `refunds.instant_refund_without_return_threshold`, `damage_claims.photo_evidence_required` and `delays.delay_threshold_days`, none of which exist in `PolicySchema` (`auto_approve_up_to`, `require_photo`, `notify_after_days_late`). Validation is bypassed and defaults silently apply.
3. The seller policy screen submits YAML with legacy keys and extra fields; `PolicySchema` has `extra="forbid"`, so publishing from the UI fails. The API/e2e/demo fixtures use the same legacy keys directly in `parsed_rules`.
4. Policy decisions and action outcomes are the same `cases.decision` string; `executed` is written by the evaluator before any provider call.
5. No persisted policy evaluation: nothing records which policy version produced a decision, and decisions cannot be explained or reproduced later.
6. No `actions` table: a refund is a mutation of `case`/`order` rows. There is no idempotency key, no provider reference, no verification record, and log-then-crash can double-pay on retry.
7. Approval approval directly resolves the case; it neither executes nor verifies the financial operation, and has no stale/cross-seller protection beyond a seller filter on the query.
8. `GET /files/{id}` lets any authenticated seller read any uploaded file.
9. Order items and tracking events are JSON, cannot be indexed or constrained, and every consumer reads a different ad-hoc shape.
10. Audit appends compute the previous hash with a read-then-insert that races under concurrency; commits are separate from the recorded operation; `verify_chain` orders by timestamp, which ties.
11. `SECRET_KEY` silently defaults to a development value in every environment.
12. No PostgreSQL integration test; SQLite-only tests cannot prove the migration works.

## 3. Proposed schema changes

New tables:

- `order_items` — normalized order lines: `order_id`, `sku`, `title`, `quantity > 0`, `unit_price_minor >= 0`, `returnable`, `category`, timestamps. Authoritative for items; `orders.items` is retained as a read-only legacy snapshot written only by `sync_order_items`.
- `tracking_events` — `shipment_id`, `event_timestamp`, `status`, `location`, `description`, `provider_event_id`, `raw_payload`, timestamps; index `(shipment_id, event_timestamp)`; partial unique index on `(shipment_id, provider_event_id)` where the provider id is present. Authoritative; `shipments.tracking_events` retained as a legacy snapshot.
- `policy_evaluations` — `case_id` (nullable for proactive delay evaluations), `seller_policy_id`, `policy_version`, `decision`, `reason_code`, `explanation`, `evaluation_result` JSON, `evaluator_version`, `evaluated_at`. Append-only: re-evaluation writes a new row.
- `actions` — `case_id`, `order_id`, `seller_id`, `action_type`, `amount_minor`, `currency`, `status`, `idempotency_key`, `external_reference`, `request_payload`, `response_payload`, `initiated_by`, `approval_id`, `failure_reason`, `completed_at`. Unique `(seller_id, idempotency_key)`; check `amount_minor >= 0`.
- `action_verifications` — `action_id`, `verification_status`, `verification_method`, `provider_reference`, `provider_response` JSON, `verification_attempt`, `verified_at`. Multiple attempts retained.
- `audit_chain_state` — one row per seller chain (`chain_key` unique) with `last_hash`, `last_sequence`, `updated_at`, used as a locked chain head.

Changed tables:

- `orders`: unique `(seller_id, order_number)`; unique `(id, seller_id)` as composite FK target.
- `cases`: composite FK `(seller_id, order_id) -> orders(seller_id, id)` prevents cross-seller cases at the database level. Buyer consistency with the order is enforced in the centralized resolution service and tested (a composite buyer FK would break orders that are not yet claimed by a buyer).
- `seller_policies`: unique `(seller_id, version)`; partial unique index on `seller_id` where `is_active`; migration deactivates all but the highest version per seller.
- `approval_requests`: `policy_evaluation_id`, `action_id`, `requested_amount_minor`, `currency`, `approved_by` (users FK), `expires_at`, `decision_reason`; statuses extend to `expired` and `cancelled`.
- `audit_logs`: `chain_key` (seller id or `__global__`) and `sequence`; unique `(chain_key, sequence)`.
- All model JSON columns use a portable `JSON` type with a PostgreSQL `JSONB` variant.

Retained JSON (with reasons): `users`/`buyers` shipping address, `seller_operations` pincode/courier lists and business hours, `seller_policies.parsed_rules` (validated snapshot), `case_messages.tool_calls`, `approval_requests.requested_action` / `auto_evaluation_summary`, `audit_logs.payload`, `policy_evaluations.evaluation_result`, provider payloads. These are documents, not relationally queried entities.

## 4. Migration strategy

- Never rewrite `73fa33a3a744` or `3d74bdde4fe4`. One new incremental revision adds the tables, constraints, indexes and columns, and backfills: `orders.items` -> `order_items`, `shipments.tracking_events` -> `tracking_events`, `audit_logs.chain_key`/`sequence` and `audit_chain_state`.
- Backfills run in the migration because they are pure copies of existing rows; counters are validated (`source count == copied count`) and the migration fails loudly on violation. The SQLite-to-PostgreSQL data transfer is a separate explicit utility (`scripts/migrate_sqlite_to_postgres.py`), never hidden inside a schema revision.
- Duplicate or inconsistent rows (duplicate order numbers per seller, duplicate policy versions, cases whose order belongs to another seller) abort the migration with a descriptive error instead of being silently dropped.
- Downgrade removes the new constraints/columns and drops the new tables. Dropping `order_items` / `tracking_events` is destructive and documented as such (the legacy JSON snapshots remain intact).
- `orders.items` and `shipments.tracking_events` stay for compatibility; they are written only through `sync_order_items` / `sync_tracking_events`, so the normalized tables never disagree with the snapshot the API returns.

## 7. Compatibility risks

- `cases.decision` must keep emitting `executed | needs_approval | not_eligible` for the UI badges, while the real policy decision lives in `policy_evaluations.decision` (`eligible | needs_approval | not_eligible | manual_review`). `manual_review` maps to the `needs_approval` badge and creates an approval request.
- Order/shipment API payloads keep their JSON shapes by serializing the normalized rows back into the legacy shape; readers fall back to the legacy JSON when no normalized rows exist.
- Policy YAML keeps the documented canonical keys and additionally accepts the keys the seller UI already submits (`auto_approve_max_amount`, `delay_threshold_days`, `photo_evidence_required`, ...). `parsed_rules` keeps emitting the compatibility keys the policy screen and public directory read.
- Policy money fields stay in major units (the documented contract); every calculation converts once at the engine boundary into integer minor units.
- The SQLite in-memory test fixture remains supported, but partial indexes and composite FKs are only proven on PostgreSQL (`test_postgres_integration.py`).

## 8. Testing plan

- Keep all existing test files unchanged unless a genuine contract moved; rerun the full suite after each stage.
- New unit tests for every policy guard and its boundary (window limit exactly, ceiling exactly, COD restrictions, fraud limit, seller states, missing policy, missing shipment, duplicate claim, version changes, determinism).
- Constraint tests on a foreign-key-enforcing engine: unique seller/order number, policy version, order item checks, case/order/seller mismatch, action idempotency uniqueness, cascade and rollback behaviour.
- Action tests with configurable mock providers: success, failure, timeout, retry after timeout, duplicate and concurrent duplicate, verification success/failure, wallet credit duplication, return-label failure, approval-before-execution, stale approval.
- Monitor tests with injected clock: eligible compensation, repeated cycles produce one credit, missing tracking skipped, failure retriable, compensation never exceeds the approved policy.
- PostgreSQL integration test (opt-in through `TEST_POSTGRES_URL`) running `alembic upgrade head` on a fresh database and exercising JSON, constraints and idempotency. SQLite results are not accepted as proof of PostgreSQL support.
- `scripts/run-e2e-scenarios.py` updated to the real schema and the approval -> execution -> verification path; it refuses to run against a production environment or a non-SQLite database unless explicitly allowed.
- Final gates: `pytest`, `ruff`, `mypy`, frontend `lint` and `build`, repository scanners, plus a real `alembic upgrade head` and query check against the Docker PostgreSQL instance.
